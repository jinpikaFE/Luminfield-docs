# 中央主城与放射式大世界布局

## 背景

旧布局把主要建筑、NPC 与交互压缩在偏小且偏置的城区，同时让外围探索区依赖高密度随机物件填充。结果是主要内容过度集中、跨区绕行明显，而大地图虽然面积充足却缺少可辨认的区域构图。

## 决策

1. 保持世界 192×128、七区域、32×32 流式区块、稳定 ID 和 schema v1 不变。
2. 把微光城固定到 `(64,32)–(127,95)` 的世界中央 64×64 格范围，以 `(96,64)` 为四向主路交点。
3. 六栋可进入建筑、11 处既有地标、16 名 NPC 日程和三个节日返回点随城区整体迁移，不创建平行人物、建筑或节日状态。
4. 外围随机环境物件密度降到约 15%，使用 34 处固定构图与 8 处大型原创景观建立区域差异；道路、资源、碰撞和探索状态仍由 Core 定义。
5. 旧存档玩家若落在新布局阻挡格，载入时移动到最近安全格；其他日期、库存、任务、资源、NPC 和探索进度不变。
6. 本轮只重制世界空间和视觉。现有 `ConstructionSystem` 继续负责预设项目施工；自由 `BuildingSystem` 作为后续玩法另行设计。

## 原因

- 中央枢纽缩短家园、城区和各外围区域之间的基础通勤距离。
- 固定构图与大型景观为每个区域提供可记忆地标，同时保留流式加载和稳定状态合同。
- 降低随机密度可减少视觉噪声和重复感，让资源、道路、目标提示与 NPC 更易辨认。
- 保持世界尺寸、稳定 ID 与存档 schema 能控制迁移风险，不让一次布局重制演变为业务状态重写。

## 后果

- 后续新增区域内容应优先扩展区域专属构图、事件和资源组合，而不是重新提高通用随机物件密度。
- 任何新增建筑或景观必须保留四向道路、NPC 路线、关键入口与旧档安全落点。
- 自由建筑需要单独冻结可建区、占地、施工、升级、容量、拆改、预览、存档和 NPC/道路保留区合同后才能实施。
- 截图 374–379 作为本次中央城区和五处外围景观的 macOS 视觉基线；Windows/Linux 需在对应系统另行验收。
