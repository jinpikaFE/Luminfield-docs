# 业务动作先检查、模拟，再原子提交

## 背景

制作、加工、购买、委托、星灯、施工和邮件会同时修改库存、货币与另一个领域状态。先扣除一部分再发现容量或条件不足，会导致丢物、重复领奖和预览/动作不一致。

## 决策

1. 动作先检查场景、工具、目标、业务状态、体力、水量、材料、货币和容量。
2. 涉及多项库存变化时，在槽位副本上模拟完整移除与完整加入。
3. 只有全部条件和模拟均成功，才一次提交库存与领域状态。
4. 任务、技能、关系或教程进度只在主动作成功后记录。
5. 任一失败分支必须保持所有业务状态不变，并返回稳定本地化原因。

## 原因

- 玩家不会因背包已满、闭店或重复操作丢失资源。
- 预览可以在动作前准确解释结果。
- 失败零副作用可通过状态快照测试明确验证。
- 批量领取和多奖励任务不需要补偿性回滚。

## 后果

- 新增复合动作应优先复用 `Inventory.TryExchange`、`TryRemoveMany`、`TryRemoveFamilies` 或 `TryAddMany`。
- 不能用 UI 禁用按钮代替领域层校验。
- 无法在一次模拟中表达的动作必须先明确新的事务边界。
